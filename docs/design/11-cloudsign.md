# クラウドサイン導入ガイド・連携の設計方針

2026-10-16確認。**導入検討用の設計追記。連携コード・契約画面・DB・Webhook・アカウント設定は未実装/未実施。R4までの実装範囲、R5の停止条件、残工数38〜68時間を変更しない。** 以下は公式に確認したサービス仕様と、このプラットフォームへの導入案を区別して読む。

## 1. 何を電子契約にするか

初めに紹介会社と求人企業の人材紹介基本契約・紹介手数料に関する合意を候補にする。契約当事者、署名権限者、社内承認者、ひな形の正本は導入先が決める。候補者の個人情報提供への同意、雇用契約、採用決定、請求書は別の業務であり、同じ承認や状態にまとめない。

- 採用決定だけで契約を送らず、契約締結だけで推薦・採用・請求・入金を確定しない。
- レジュメ原本を契約の添付として自動送付しない。共有先や目的の確認なしに候補者情報を外部へ複製しない。
- 本プロトタイプの「架空情報の共有確認」は実在する本人からの法的な同意取得を実装したものではない。実契約の条項・電子契約の適用可否・保存要件は担当部門と確認する。

## 2. 最小の導入：まずクラウドサイン画面で運用

API開発を始める前に、契約の種類と件数、承認経路、宛先間違いのリスクを確かめる。クラウドサインの標準画面で契約書を作成・確認・送信し、契約の管理も同サービス上で行う。プラットフォーム側の契約状態表示やURL保存機能は現在存在しないため、ここは導入先の運用手順として切り出す。

1. 契約ひな形、当事者、送信者、承認者、受信者と署名順序を決定する。
2. 導入先が利用プラン・送信課金・管理権限・サポート範囲を確認し、必要な契約/申し込みを行う。今回、契約や課金操作はしない。
3. 指定されたテスト用の宛先と架空PDFで、送信前確認、締結、却下/取消、メール不達時の連絡を一巡する。実在する候補者の情報を使わない。
4. 締結済み原本と合意締結証明書の保管担当、アクセス権限、保管期間、復旧・退職者対応を決める。
5. 手作業の負担や転記ミスが具体化した場合に、下記API連携の対象と予算を別途承認する。

## 3. API連携を採用するときの準備

### 公式情報で確認した設定

Web APIの対象としてスタンダード/コーポレート/ビジネス/エンタープライズの各プランが案内されている。利用可否、追加費用、契約条件は導入先の契約で確認する。プランによって使えないエンドポイントもあるため、チーム全体の書類取得を前提にしない。[公式Web API概要](https://help.cloudsign.jp/ja/articles/936884)

管理画面の「Web API設定」で利用を有効にし、テストには本番と分離されたSandboxを申し込む。API接続先は本番 `https://api.cloudsign.jp`、Sandbox `https://api-sandbox.cloudsign.jp`。[公式利用ガイド](https://help.cloudsign.jp/ja/articles/2681259)

クライアントIDは秘密として扱う。メンバー本人の発行か管理者による発行かをチームで選択できる。サービスごとのID発行が推奨されている。[IDの発行手順](https://help.cloudsign.jp/ja/articles/3761788)、[管理者の設定手順](https://help.cloudsign.jp/ja/management-of-web-api-usage)

### このシステムへの導入案

| 項目 | 方針案 |
| --- | --- |
| 接続単位 | 内部org ID、環境、契約送信者の組合せを明示的に登録。共有の強権限IDで全組織の契約を検索しない |
| 資格情報 | サーバーだけが取得するSecret Manager等に保管。クライアントID/tokenをGit、ブラウザ、下書き、ログ、画面写真に含めない |
| 認証方式 | Web API用クライアントIDでtokenを取得。アプリ利用者のOIDCセッションと混同しない |
| 環境分離 | APIホストと資格情報を本番/Sandboxで固定し、ブラウザ入力からホストを指定させない。起動時に環境不一致を拒否 |
| 出口通信 | 承認したAPIホストへのHTTPSのみ。任意URL取得やWebhook本文のURLへの追従を禁止 |
| 権限 | 送信担当と承認担当を決め、現行の本人/組織認可を通して操作。組織管理や契約権限の新設は別設計 |
| 切替 | Sandbox受入後に本番接続先と本番資格情報を設定し、宛先・PDF・承認者を再確認して限定運用 |

tokenは `POST /token` で取得し、Bearerとして使用する。公式の有効期間は3,600秒。実装時は応答の`expires_in`を参照し、期限前更新を直列化する。401で認証更新が必要でも、送信操作を無条件再実行しない。[公式利用ガイド](https://help.cloudsign.jp/ja/articles/2681259)

## 4. 契約送信の流れ（実装案）

| 段階 | 業務上の動き | 外部APIの対応 |
| --- | --- | --- |
| 作成 | 契約の当事者・内容を入力し、内部の契約下書きを作る | まだ外部へ送らない |
| 準備 | 承認対象のPDF・宛先・署名順を固定する | `POST /documents`、`POST /documents/{documentID}/files`、`POST /documents/{documentID}/participants`。入力欄が必要ならwidgetsの設定も行う |
| 承認 | PDF、受信者一覧、順序、送信者を人が確認する | 初回は自動承認しない。承認後のPDF/宛先変更は承認を無効化 |
| 送信 | 明示操作で送信予定を永続化する | `POST /documents/{documentID}` |
| 照合 | 先方確認中/完了/取消等を外部の正本と照合する | `GET /documents/{documentID}`、Webhookと定期照合 |
| 保管 | 締結原本と証明書を権限付きで保管する | ファイル取得、`GET /documents/{documentID}/certificate` |

上記のAPI名は公式利用ガイドで確認したもの。API仕様書本体は今回の取得ツールでは閲覧できなかった。要求項目、署名位置、PDF条件、エラー、利用可能プランの詳細は実装着手時に[公式API仕様書](https://app.swaggerhub.com/api/CloudSign/cloudsign-web_api/)の採用版で再確認する。現在の設計だけでAPI接続確認済みとはしない。[操作の公式説明](https://help.cloudsign.jp/ja/articles/2681259)

### 二重送信・応答喪失をどう扱うか

**送信APIは、既に先方確認中の書類に対して呼ぶとリマインドになる。** 送信とリマインドを別操作として扱い、タイムアウトを理由にPOSTを繰り返さない。[公式の送信/リマインド仕様](https://help.cloudsign.jp/ja/articles/2681259)

このシステム側ではorg/契約ID/操作IDで直列化し、PDF hash・宛先とその版・外部document ID・送信試行・結果不明を記録するoutbox方式を検討する。外部呼出しと内部DBを一つのtransactionで原子的に確定できるとは扱わない。

- 外部document IDが分かる場合はGETで現在状態を確認し、送信済みなら再送しない。
- 作成APIの応答が失われ、外部IDも不明なら自動で作り直さず、照合待ちにして担当者へ案内する。外部冪等キーや照合用metadataの可否は採用API版で確認するまで仮定しない。
- 内部再実行防止の記録は、R4の7日TTLをそのまま流用せず、契約の保存・監査期間に合わせて別途決定する。
- 429は待機、5xx/通信断は結果不明を区別する。送信を止めても既に相手へ届いたメールや成立済み契約は取り消せない。再開時は照合を先にする。

## 5. Webhookと状態の整合（実装案）

公式の通知対象は締結完了、取消/却下、メール不達。Web API設定から通知URLと条件を登録でき、テスト送信機能もある。設定先は公開HTTPSの受信専用経路にし、一般業務APIやログイン済みブラウザからの操作経路と分ける。[Webhookの設定方法](https://help.cloudsign.jp/ja/articles/417935)

公式の挙動では2xxと4xxは再送されず、5xxは10分間隔で最大3回の自動再送となる。永続受信できたときだけ2xxを返し、一時的な保存障害は5xxにする。再送だけに依存せず定期照合と手動照合を用意する。[Webhook実行仕様](https://help.cloudsign.jp/ja/articles/9977727)

以下は本システムの安全対策案であり、クラウドサイン側に同じ仕組みがあるとの主張ではない。

1. 公式の送信元IPを導入時に再確認して入口で制限する。ロードバランサ経由の実IPの扱いと、送信元変更時の更新責任者を決める。
2. 確認した公式説明には署名ヘッダの仕様がないため、架空のHMAC検証を設計しない。User-Agentや本文emailだけを認証の根拠にしない。利用可能な追加認証は提供元へ確認する。
3. 既に内部で紐付けた環境/接続/org/外部document ID以外は契約状態へ反映しない。本文userIDや任意URLからorgを決めない。
4. 受信サイズ・頻度を制限し、必要最小限の受信台帳を永続化した後、サーバーから正しい接続のAPIへGETして状態を再確認する。本文の状態だけで「締結済み」にしない。
5. 重複・順序逆転・通知欠落・不達を扱い、GETの結果と履歴を照合する。不達は配送エラーであり、契約成立/採用結果を覆す状態として扱わない。
6. 固定のテスト送信や未知の書類は業務反映せず、許容した形式なら受信確認と運用通知を行う。未知の相手の存在や契約内容を応答に含めない。

## 6. データ・閲覧・保管の案

契約はレジュメの`documents`とは別モデルにする。候補は `contracts`（内部org/当事者/承認版/状態）、`contract_files`（不変原本/hash/外部ID）、`contract_operations`（操作/照合/再実行防止）、`contract_events`（受信/照合/監査）。名称・列・RLSは実装前にレビューし、今回はmigrationを作らない。

- 契約のアクセス範囲は送信組織の権限を基点に別途定義する。クラウドサイン上の受信者であることだけで、このアプリの組織や管理権限を付与しない。
- 採用後のレジュメ共有取消と契約の有効性/保管義務を混同しない。契約書を企業へ見せるアプリ内機能も現在はない。
- 締結PDF/証明書は改変せず原本bytes/hashを保持する。署名を壊す変換や「無害化済みファイル」への置換をしない。取得元確認・検疫・AV/安全なattachment配信の条件は契約用に設計する。レジュメの形式policyを無条件に再利用しない。
- 閲覧/ダウンロードをAPIで認可し、外部IDや保存キーを知るだけでは取得できない。定期照合jobにも接続/org単位の制限をかける。
- 保管期間、利用終了時の扱い、原本と監査記録のバックアップ/復旧、外部サービスへのデータ移転は導入先と合意する。下書きの7日後に契約原本を削除する設計にしない。
