# 実装順序と受入計画

## 実装前に解決する項目

| 項目 | 決め方・証拠 |
| --- | --- |
| 依存バージョン | サポート期間と一次資料を確認、lockfileとコンテナdigestを固定 |
| ライセンス | Apache-2.0候補。配布物・依存・フォント・PDF検査ツールの互換性確認後にLICENSEを追加 |
| 日本語PDF | 固定テンプレート、日本語フォント、複数ページ、長い氏名でレンダラーの実出力を確認 |
| PDF検査 | parser/検査ツールを選定し、正常・破損・暗号化・active contentのfixtureで拒否条件を確認 |
| OIDC | ブラウザとコンテナ間のissuer/redirect整合を確認し、検証を省略せずログイン成立 |
| 実装の作業枠 | オーナーが実装着手と時間上限を指定。設計の完成を実装承認として扱わない |

## 作業順序と時間の仮説

1名でAI支援を使う場合、40〜100時間を最初の計画幅とする。これは実績のない目標で、完成期限の約束・本番工数・AIの短縮率の測定ではない。以下の各行を下限/上限で合算すると40/100時間。実装開始後、作業分類ごとに人の確認時間も含めて記録し、未解決の難所が出た時点で残作業を再評価する。

| 段階 | 内容 | 時間仮説 | 完了を示す証拠 |
| --- | --- | ---: | --- |
| M1 | 起動、依存、OIDC、所属、session | 6〜12時間 | 新しい環境でログイン/ログアウト、所属なし拒否 |
| M2 | 求人、保存、候補者 | 6〜12時間 | 2組織ずつのCRUDと他組織拒否 |
| M3 | PDFレジュメ | 6〜14時間 | 正常取得、不正PDF拒否、他組織・企業原本アクセス拒否 |
| M4 | 推薦・選考・snapshot・RLS | 8〜18時間 | 一巡、競合、重複送信、辞退と共有撤回 |
| M5 | 通知モック・請求PDF | 4〜10時間 | 未送信表示、日本語PDF、再取得で採用記録が増えない |
| M6 | E2E・API認可・CI | 6〜16時間 | 後述の受入条件と失敗再現の記録 |
| M7 | 起動/操作文書、配布イメージ | 4〜18時間 | 第三者のローカル起動と操作、画像/ライセンス一覧 |
| 合計 | ローカルで動くプロトタイプ | 40〜100時間 | 未検証事項も含む成果物記録 |

3クラウドのTerraform実装・クラウド実地検証、LP本文とサイト制作、包括的な商用運用ガイド、データ移行、本番運用はこの時間幅に含めない。基本認可や最低限の異常系を外して時間内に収めない。サブエージェント利用や別作業への分割を時間上限の迂回に使わない。

## 必須の受入条件

| ID | 検証 | 期待する結果 |
| --- | --- | --- |
| A01 | 完全な操作一巡 | 求人登録から採用・デモ請求PDFまでブラウザで成立、再ログイン後も維持 |
| A02 | ID差替えによる越権 | B/YにA/Xのcandidate/application/document/PDF/通知が返らない |
| A03 | 未提出候補者 | 企業はdraftの推薦・候補者原本を取得できない |
| A04 | 共有snapshot | 提出後のcandidate変更が既存推薦に反映されない |
| A05 | 辞退・共有撤回 | 企業のsnapshot/PDF取得を拒否。既に取得されたPDFは回収不可と表示 |
| A06 | 同時更新 | 2タブの古いversionで上書きできない。イベントも1件のみ |
| A07 | 推薦リトライ | 同じキーで同じ案件、異なるpayloadは409、二重推薦制約が有効 |
| A08 | 採用リトライ | placementが1件、通知が重複しない、PDF再表示で発行処理しない |
| A09 | PDF異常・renderer停止 | PDF不正/容量超過を拒否。生成障害で503/504、復旧後に再試行可 |
| A10 | session/CSRF | 期限切れ401、logout後不可、CSRF/Origin不正で更新不可 |
| A11 | poolとRLS | 組織A/Bで接続再利用しても漏えいなし。通常DBロールによる越権SELECTが失敗 |
| A12 | UI | keyboard、日本語長文、拡大、空状態、エラー、狭い画面で主操作を完了 |
| A13 | 秘密・ログ | Git/配布物/ログに秘密・候補者本文なし、auditで操作追跡可能 |

API試験とブラウザE2Eを区別する。PDFは文字抽出だけでなく画面で日本語・改ページ・デモ表記を確認する。UIモック、ビルド成功、E2E成功、本番利用可能を同じ意味で報告しない。

CIはformat/lint/typecheck、Rustのdomainと認可試験、実DB/RLSの結合試験、Compose上の主要E2E、依存・配布イメージの確認を実装する。CIやテストコードは今回まだ作らない。

## 性能の確認方法

生成求人15,000件・生成組織2,000件を任意の負荷fixtureとして作り、環境(CPU/メモリ/DB/同時利用)、検索条件、時間分布、失敗数を記録する。これは実在の利用者や本番データではない。合格する性能値は利用環境の要件と測定を基に実装時に決める。件数だけで「十分速い」と断定しない。

## 引渡し時に添える記録

commit、起動した環境、操作動画または画像、通過した受入条件、失敗/未検証事項、実工数、再現手順を記録する。クラウド課金・公開環境・実データ利用の判断は、ローカルデモの完成とは別に行う。
