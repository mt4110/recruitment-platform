# 実装順序と受入計画

## v0.3の前提

1名でAI支援を使い、コードが空の状態からローカルで一巡できるOSSプロトタイプを作る計画。1ユーザー1組織、固定1ページ/1明細の請求PDF、架空データ専用。認証、組織分離、共有失効、PDF検査/復旧、必要な検証は含める。

確認対象はmacOS/Apple SiliconのDocker Compose開発環境と、Linux/amd64のCI環境、各環境のChromium。OS/runtimeのversionとimage digestはM0で記録する。全OS・全ブラウザの保証は行わず、この対象で新規起動を確認する。

## 工数の見直し

**80〜140時間の仮積算**へ改める。各機能の設計上の作業を積み直した計画幅であり、実績・見積契約・作業予算の承認ではない。AIによる削減率や、100時間以内の完成を保証する根拠はまだない。実装・人の確認/原因調査・CIの整備・文書・引渡し確認を含む作業時間。単なる実行待ちや依頼先との日程待ちとは分けて記録する。

| 段階 | 内容 | 時間仮説 | 完了を示す証拠 |
| --- | --- | ---: | --- |
| M0 | 依存/ライセンス、OIDC経路、RLS共有、PDF検査/1ページの技術確認 | 4〜8時間 | 後述の未検証契約を実環境で確認 |
| M1 | 7コンテナ起動、認証、唯一の所属、session/CSRF、fixture | 12〜20時間 | 新環境で4アカウントのlogin/logout、未登録/無効を拒否 |
| M2 | 求人、保存、候補者のUI/API、入力検証 | 12〜20時間 | 求人公開/終了、候補者更新、他組織の拒否 |
| M3 | PDF service検査、upload/冪等/lease/復旧/配信 | 12〜20時間 | 正常/拒否/中断/再試行、検査policyと不変ファイル |
| M4 | 推薦/選考、snapshot、RLS、辞退/撤回、job lock、冪等/監査 | 16〜28時間 | 共有権限と状態表、競合/応答喪失/通常DBロールでの確認 |
| M5 | 通知モック、固定1ページ請求PDF | 4〜8時間 | 未送信表示、日本語と長い組織名、page count=1 |
| M6 | API/RLS結合試験、ブラウザE2E、CI、配布物確認 | 14〜24時間 | 下記受入条件、失敗再現と修正の記録 |
| M7 | 起動/操作文書、配布イメージ、第三者の再現確認 | 6〜12時間 | 記載手順から起動と一巡、実工数と既知制約 |
| 合計 | ローカルプロトタイプの引渡し | 80〜140時間 | 各行の下限/上限を単純合算 |

下限は技術確認が想定どおり通り、既存UI部品を使い、大きな依存問題や設計変更が起きない場合。上限も未発見問題をすべて吸収する保証ではない。M0の確認結果を各機能の実装で再利用し、同じ作業を二重計上しない。M6はそれらをまたぐ回帰/E2E/CIと修正の枠。

40時間は一巡の進捗・既知の障害・残工数を示す確認時点とする。100時間でも未完了なら、完了した受入条件と残作業を示して判断を求める。**140時間という計画値を予算延長の承認として扱わない**。実装開始前にオーナーが指定する作業上限が優先する。上限に達したら停止し、安全条件や受入期待値を下げて完成扱いにしない。

3クラウドのadapter/Terraform実装・課金を伴う実地検証、LP本文/サイト、包括的商用運用ガイド、データ移行、外部連携、本番運用は別の作業。組織切替・複数所属と自由な請求明細/複数ページは初期版に含めない。

## M0で確認する契約

| 項目 | 確認内容・失敗時 |
| --- | --- |
| 依存/ライセンス | サポート対象versionとlockfile/image digest、pikepdf/libqpdf・フォント・配布物のライセンスを確認。Apache-2.0候補のLICENSEは確認後に追加 |
| OIDC | issuer/redirectがブラウザとコンテナで整合し、検証省略なしで4アカウントを使い分けられる |
| RLS共有とjob lock | 通常ロールの共有参照取得、辞退後拒否、agencyのjob UPDATE拒否を維持したadvisory lockによる競合制御 |
| PDF | static-resume-v1の通常静的PDFと構造属性/Aを持つタグ付きPDFの許可、破損/暗号化/active content・文脈偽装・属性配下の禁止要素の拒否、制限超過を許可しない、日本語固定1ページ |

各技術確認は最大2時間の小さな単位に区切る提案。実装着手の承認と作業枠を得てから実施する。想定の方式/対応範囲で成立しない場合、結果と代案・残工数を示して設計を見直す。今回、この技術確認を実行したとは扱わない。

2026-10-15のM0ローカル分は[結果記録](../validation/2026-10-15-m0-report.md)に保存した。Linux/amd64実機の残件は、製品実装から独立した[検証手順](../../validation/m0/README.md)と手動workflowで確認する。M0の両環境が成立した場合に限り、今回承認された次段階をM1（7サービスの起動・認証・所属・session/CSRF・初期データ）までとし、M2へ進む前に結果と残工数を報告する。

## 必須の受入条件

| ID | 検証 | 期待する結果 |
| --- | --- | --- |
| A01 | 一巡と唯一の所属 | 4アカウント各1組織、組織切替なし。求人登録から採用/請求PDF、再ログイン後も維持 |
| A02 | ID差替え | B/YにA/Xの候補者・推薦・文書・通知が返らない。storage参照をJSONへ出さない |
| A03 | 未提出と原本 | 企業はdraftと候補者/document原本を読めず、E_SHARED時の共有参照だけ取得可 |
| A04 | snapshotと募集終了後 | candidate/job編集が提出済み内容を変えない。閉じた求人も推薦のjob snapshotは表示可 |
| A05 | 全状態の共有閲覧 | draft/withdrawn/撤回済みは企業の候補者/PDFを404、共有有効なsubmitted/screening/rejected/hiredは可。直接URLでも確認 |
| A06 | version競合 | 2タブの古いversionで上書き不可、eventは一度のみ |
| A07 | 冪等性 | 同キー同時/応答喪失後の古いversion付き再要求が同じresourceを参照、異payloadは409、二重処理なし。upload完了→応答喪失→候補者アーカイブ後も、保持期間内の同bytes/同キーは同document/201、新キーは409 CANDIDATE_ARCHIVED。現在の認可を失えば再送も拒否 |
| A08 | 採用と固定1ページPDF | placement一度のみ。共有失効後も維持。A4縦/1明細/1ページ、日本語・長い組織名・デモ表記 |
| A09 | PDF許可/拒否・隔離 | 通常静的PDFと有効な構造属性/Aを持つタグ付きPDFは許可。型名の偽装・アクションとの参照共有・属性配下の禁止要素は拒否。暗号化/破損/禁止要素/深さ・object数・時間・容量超過は拒否/保留、renderer障害503/504、再試行可能 |
| A10 | session/CSRF | 無効user/組織、期限切れ、logout後、CSRF/Origin不正を拒否。他アカウントへの自動再送なし |
| A11 | pool/RLS | A/Bで接続再利用しても漏えいなし。通常DBロールで自社以外の原本拒否、企業の共有参照は正しく許可/失効 |
| A12 | UI | keyboard、長い日本語、拡大、空/失敗/処理中状態、狭い画面で主操作完了 |
| A13 | secretと監査 | 配布物/Git/logに秘密/候補者本文なし。rollbackした拒否もsecurity logで追跡 |
| A14 | 募集終了/編集と提出 | 双方向の先行順で、終了先なら提出拒否、提出先ならcommit後に終了。job/candidate version不一致はsnapshotを作らない |
| A15 | 全状態の共有撤回 | draft拒否、進行中は辞退同時、終端は状態/placement維持、重複はno-op、再共有なし |
| A16 | upload中断と復旧 | DB予約commit前の停止では未検査stagingを公開せず、同要求の再送で初めて単一documentを予約し孤立stagingを管理。予約commit後の検査前/合格後/配置後/ready commit前の停止ではlease切れ後に同document IDと冪等記録で復旧。重複不可、hash違いは停止、readyを消さない |

A05の失効保証は撤回commit後の新しい要求。既に取得/stream開始したPDFの回収はできない。API試験とブラウザ試験を分け、PDFは文字抽出/page countに加えて日本語・配置を目視確認する。

CIはformat/lint/typecheck、Rustのdomain/認可、実DB/RLSとlock/冪等の結合試験、Compose上の主要E2E、依存・image確認を実装する。今回、テストコード/CI/アプリは作成しない。

## 性能と引渡し記録

大規模fixtureは基本受入後の任意項目とする。実施する場合は生成求人15,000件等について環境・入力・同時利用・時間分布・失敗数を記録する。実在ユーザーや測定済み性能と混同しない。性能合格値は対象環境の要件から実装段階で決める。

引渡しにはcommit、環境、起動/操作の画像または動画、受入の結果/未検証、作業分類別実工数、再現手順を付ける。ビルド、UIデモ、E2E、実運用の判定を区別する。
