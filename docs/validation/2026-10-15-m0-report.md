# M0 技術確認結果

2026-10-15 / 設計基準commit: 22161808daa4c86052bef02326fd270371d5245d / 対象設計 v0.3

## 結論

**認証・RLS・PDF検査・固定1ページ生成は、macOS/Apple Silicon上のLinux/arm64コンテナで技術的に成立した。** ただし、設計が確認対象に含めているLinux/amd64の実機CIは今回未確認。M0のローカル分を確認済みとし、全対象環境の合格とは扱わない。

本実装は開始していない。認証用の一時的なPython検証サーバー、最小SQL、PDF検証スクリプトを製品リポジトリ外で実行した。Rust/Axum API、Next.js画面、本番用migration、7サービスのCompose、製品用CIは作っていない。本実装へ進むかは、この結果を見てオーナーが判断する。

## 1. 認証

ブラウザとコンテナ内RPの両方で、issuerを `http://idp.m0.localhost:18080/realms/m0` に固定した。ブラウザはlocalhostの経路、コンテナはDocker network aliasで同じ名前に到達する。ホストのhostsファイル、TLS/署名検証の無効化、トークンの書換えによる成功扱いは使っていない。HTTPはローカル検証に限定した。

- 紹介会社A/B、求人企業X/Yの4利用者がAuthorization Code + PKCEでログインできた。
- `(issuer, sub)` の所属は、検証用realmの管理APIから取得したIDと固定所属の対応で照合した。メールやlogin_hintによる自動所属・自動登録は行っていない。未登録利用者は403で拒否した。
- state/nonce不一致、PKCE verifier不一致・challenge欠落、署名改変、issuer/audience不一致、実際に期限切れになったID token、未登録redirect URIを拒否した。拒否理由も照合した。
- auth attemptの再利用は拒否。検証用のhash化した不透明sessionとHttpOnly/SameSite=Lax cookieでログインし、CSRFなしのlogoutを拒否、正常logout後の/meを401とした。
- 同じbrowser contextでAからlogoutしBへ交代できた。Keycloakが前の利用者の再認証画面を出す場合は、標準のログインやり直し操作を経由した。`prompt=login`だけでアカウント選択を保証しない、という既存設計を維持する。

session/auth attemptは検証サーバーのメモリ内だけに置いた。8時間sessionの実経過、5分attempt期限の実経過、無効化後のDB再照合、API再起動後の状態維持まで確認した結果ではない。KeycloakはM0用のstart-dev/H2であり、設計のKeycloak用PostgreSQLとの接続はM1の起動確認に残る。

## 2. RLSと募集終了/提出の競合

`m0_runtime`をnon-owner・NOSUPERUSER・NOBYPASSRLSのloginロールとし、各検証テーブルでENABLE/FORCE RLSを有効にした。管理ロールを使ったのは検証schema/fixtureの作成と状態準備だけで、確認対象クエリは通常ロールの別接続で実行した。

- org contextなしでは行を返さない。
- A/Bは自社の原本文書のみ、X/Yは許可された共有参照のみ取得できる。Xは原本を読めず、共有行のstorage参照から取得先を解決できた。
- draft/withdrawnは企業に共有せず、submitted/screening/rejected/hiredは共有有効時だけ許可する。撤回commit後は共有行を返さず、案件metadataと自社agencyの閲覧は維持した。
- 同一接続を使い回しても、commit後にはSET LOCALのorg contextが残らなかった。SQLx pool自体の試験ではない。
- agencyのjob UPDATEはRLSで0行となり、変更できなかった。
- 共通のtransaction-level advisory lockで、募集終了先行なら提出をJOB_NOT_OPENとして受け付けず、提出先行なら受付記録のcommit後に募集終了が進んだ。待ち上限3秒ではLockNotAvailableとなり、rollbackできた。

競合の受付記録は検証専用テーブルを使った。snapshot/event/通知/placementを含む製品の推薦transactionや、冪等性・upload lease・中断復旧の試験を代行したものではない。

## 3. PDF検査

Linux子process内で `attempt_recovery=False`、`is_encrypted`、`check_pdf_syntax`、`get_warnings` と全間接/直接オブジェクトの走査が使えることを確認した。

許可したのは通常の静的PDF、構造属性/Aを持つタグ付きPDF、属性revision配列を持つタグ付きPDF。拒否したのは破損、空password暗号化、JavaScript、リンク注釈、フォーム、添付、構造要素の型名偽装、アクションとの参照共有、属性配下の禁止要素、深さ超過、object数超過、21ページ、容量超過、参照されないJavaScript辞書、エスケープされた禁止keyの15例。

生成した請求PDFの3例も、この検証用policyでは受け付けられた。合成fixtureだけでなくChromiumが生成する静的PDFでの構造も確認した結果である。

検査子processのアドレス空間上限256MiB、CPU時間上限5秒、親からのwall timeout 5秒を実際に発動させた。非root、read-only root filesystem、実効capabilityなし、外向き通信不可も確認した。CPU試験とwall試験は別の入力で行った。制限の成立を確認したもので、任意の10MiB PDFが5秒以内に検査完了するという性能保証ではない。

## 4. 固定1ページ生成と必要な実行設定

[通常例](../../output/pdf/m0-2026-10-15/invoice-normal.pdf)、[長い組織名の例](../../output/pdf/m0-2026-10-15/invoice-long.pdf)、[HTML記号を含む例](../../output/pdf/m0-2026-10-15/invoice-escaped.pdf)を出力した。

3例ともA4縦・1明細・固定額500,000円・1ページ。日本語、組織名の40書記素への省略と2行内の配置、デモ表記、HTML escapeを確認した。pypdfのページ数・文字抽出とPopplerのPNG描画を併用し、3例を目視して欠け・文字化け・重なりがないことを確認した。抽出文字はCJK互換文字を含むため、文言照合にはNFKC正規化を使用した。

ChromiumのSandbox Statusで、Layer 1=Namespace、PID/Network namespaces=Yes、Seccomp-BPF=Yesを確認した。`--no-sandbox`は使っていない。

初期起動で次の問題が出たため、実装時には確認済みの設定を明示する必要がある。

| 観察した失敗 | 成立した設定 | 実装への影響 |
| --- | --- | --- |
| capabilityをすべて落とすとsandboxのchrootが失敗 | 非rootのまま、drop ALLにSYS_CHROOTだけを追加。実効capabilityは0、no-new-privileges、seccompを維持 | 「不要capabilityなし」を具体的な許可一覧にする。SYS_ADMIN/privilegedは不要だった |
| read-onlyなHOMEでは通常版ChromiumのCrashpadが起動失敗 | HOME/XDG_CONFIG_HOME/XDG_CACHE_HOMEをtmpfs内の専用ディレクトリへ配置 | root filesystemをread-onlyのまま、一時書込み先を指定する |
| 同梱Playwrightと既存のmacOS browser cacheの版が不一致 | 検証用ディレクトリへPlaywrightと対応するChromiumを取得 | package版とbrowser版をセットで固定する |

seccompは[Playwright v1.62.1の公式profile](https://github.com/microsoft/playwright/blob/v1.62.1/utils/docker/seccomp_profile.json)を使用した。全許可profileへの置換はしていない。PDF検証コンテナはnetwork=none、文書保管volume・DB認証情報なしで実行した。本実装ではAPIとの内部通信だけを許可する経路の確認が別途必要になる。

## 6. 工数への影響

**現時点では、全体80〜140時間の仮積算を増減しない。** 認証/RLS/検査の方式を捨てる必要は見つからず、PDF生成の失敗も必要な実行設定を明示することで解消した。capability・tmpfs・browser版固定は、既存のM1/M3の環境・PDF作業で扱う内容であり、新機能の追加ではない。ただし枠内に必ず収まる保証にはしない。

- 既存WBSからM0を除いたM1〜M7の単純合計は76〜132時間。この数値は今回の実測から導いた新しい見積もりではない。
- 環境準備開始からの経過時間は約26分（記録取得時点で25.55分）。ダウンロード・ビルド・試験・失敗調査・成果物確認・専用VM停止を含み、証拠JSONに開始/終了時刻を記録した。人の開発工数や同等品質の製品実装時間へ換算しない。
- 検証サーバーと最小SQLは成立を確かめるためのもの。製品コードへ移す統合・エラー処理・永続化・受入試験の工数はM1〜M7に残る。
- Linux/amd64実機CIの再現確認は残る。次の確認を最大2時間の1枠に区切る案はあるが、今回その実行環境を用意・実測していないため、所要時間は確約しない。不成立なら原因と代案を示し、残工数を再評価する。
- AI支援による削減率、100時間以内の完成、予算延長の承認には読み替えない。

## 7. 引渡し状態

報告書・証拠JSON・架空の生成PDFだけを製品リポジトリ内に保存する。検証スクリプトと秘密値はリポジトリ外の専用ディレクトリに置いた。秘密値を除いたローカル検証用archiveのhashは証拠JSONに記録し、ホストの絶対パスは共有対象に含めない。

既存のDocker default profileは起動・変更していない。M0専用サービスとVMは証拠回収後に停止し、検証用データとローカル成果物を保持する。ファイル/volume/VMの削除、クラウド利用、Gitへのcommit/push、本実装は今回行わない。

判断材料としては、ローカル実装へ進む技術的な根拠が得られた。一方、全対象環境で成立確認済みという条件で本実装を判断するなら、Linux/amd64実機CIのM0確認が残っている。
