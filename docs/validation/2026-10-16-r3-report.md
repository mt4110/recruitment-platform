# R3 書類の種類・版・複数登録・処理復帰

2026-10-16。対象はR3。R4・M5へは進まない。最終実装commitは`943e0a43f44cbd804869902229f406e1c9937b73`。arm64 / Linux/amd64の最終受入を完了した。R3で停止する。

## 変更した内容

- 履歴書・職務経歴書・その他を分け、候補者/種類ごとの不変の版番号を採番する。新規document IDを追加し、原本・提出済みsnapshotは更新しない。拒否/処理中も採番し、再試行では元IDと版を使う。並行登録は候補者/種類単位のDB lockで直列化する。
- `0008_document_versions.sql`は既存書類に登録日時/ID順の版を付ける。原本/snapshotを更新せず、独立mappingで参照する。runtimeはSELECTのみ、他社は参照不可。企業は共有中の選択済み書類の版だけ参照できる。共有失効は既存E_SHAREDのRLSに従う。
- PDF/XLSXを最大10件選択し、既存の1要求1ファイルAPIへ順に送る。同時送信1件。登録拒否後は次へ進み、障害/処理待ちはキューを止める。ファイル名・種類・版・形式・時刻・サイズ・検査状態・復旧操作を表示する。ファイル選択時の案内だけで安全と扱わず、サーバーの実AV/形式判定を正本にする。
- 推薦では版・種類・形式を表示し、初期選択なし。明示したIDだけ共有する。提出直前に候補者/求人/書類の現在の状態を取得し、変更時は確認をリセットする。サーバーでも既存の認可・同一候補者・検査合格・サイズ/hash照合を維持する。後から新版を登録しても提出済みsnapshotは変えない。
- 応答喪失時は元操作キーの結果照合を先に行う。受付済みなら元document IDへ復帰し、再アップロードしない。未予約で元Fileをまだ保持している場合のみ、明示操作で照合後に同じキー/hashの再送を行う。

## 再起動後の復帰の範囲

利用者が「受付結果の復帰リンク」をブックマーク等で保存し、再認証後に開いて照合する。URL fragmentにはuser/org/candidate ID、最大10件の操作キーと種類、形式版だけを含める。File bytes、氏名、原本名、hash、認証情報は保存しない。fragment自体はHTTP要求へ送らず、復帰時にも本人/所属/候補者一致とAPI側の認可を必要とする。リンクだけではファイルを取得できない。

端末へのリンク自動保存・未送信キューのメタデータ・フォーム入力・推薦選択の暗号化永続復元はR4/R5に残す。File bytesは後続でも保存せず、未送信ファイルは再選択する。別ブラウザの新しいcontextで、再認証→保存済みリンク→同一IDへの復帰を確認する。OS全体の再起動や電源断の実機試験は行っていない。File情報のない復帰でnot_recordedになっても未実行とは断定せず、一覧確認を案内して自動再送しない。7日間の照合期限後も再実行しない。

## 検証と途中の失敗

Browserプラグインは利用できないため、既存PlaywrightでブラウザE2Eを実行した。実AV連携は実エンジン/署名DBを使用する。ネットワーク応答喪失のみroute interceptionで再現し、受理/照合/ID/二重登録は実API/DBで確認する。新しいブラウザcontextの確認はOS再起動試験と区別する。

最初のarm64起動は30GiBのDocker用VMの容量不足でDB初期化に失敗した。利用者の承認後、既存データを残して60GiBへ拡張・再起動し、空き約29GiBと元デモ7サービスのhealthy/HTTP 200への復帰を確認した。既存コンテナ/volume/証拠の削除、デモへのmigration/新実装反映は行っていない。

その後の局所R3試験は7/9成功。2件は実画面の通知role=alertに対しテストがstatusを参照したセレクター誤りだった。期待する業務状態を維持して通知のroleを修正した。最初の全件実行は73/76成功で、同じ文言の重複1件とNext.jsのroute announcerも拾うセレクター2件が失敗した。説明文を整理し、通知の探索範囲を業務画面内へ絞った。受付照合後の案内も完了を示す文言へ修正した。修正前のCI（38829113130 / 38830375517）は打切り、最終commitで両archの全件を再実行した。途中の失敗を合格として扱わない。
